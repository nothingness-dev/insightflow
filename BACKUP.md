# InsightFlow customer-server backup and recovery

The backup system is for a Linux server running the application with Docker Compose. A full backup contains the PostgreSQL database, all uploaded media, deployment configuration, Nginx configuration, SSL files when present, a manifest, and SHA-256 checksums.

Redis and generated static files are intentionally excluded: Redis is disposable cache data and static files are regenerated by the backend container.

## Install on the customer server

The examples assume the project is installed at `/opt/InsightFlow`:

```bash
cd /opt/InsightFlow
chmod +x backup.sh
sudo mkdir -p /opt/InsightFlow/backups
sudo chown "$USER":"$USER" /opt/InsightFlow/backups
chmod 700 /opt/InsightFlow/backups
```

The script automatically selects `docker-compose.customer.yml` when that file exists. Create and verify the first backup while the application is running:

```bash
./backup.sh backup
./backup.sh list
./backup.sh verify latest
```

Backups default to `/opt/InsightFlow/backups` and are retained for 30 days. Prefer a separately mounted disk or network share:

```bash
BACKUP_DIR=/mnt/backup/InsightFlow BACKUP_KEEP_DAYS=90 ./backup.sh backup
```

## Enable automatic backups

Install a daily 02:00 cron entry under the current user:

```bash
cd /opt/InsightFlow
./backup.sh install-cron
crontab -l
```

Choose another schedule or retention period if needed:

```bash
BACKUP_CRON_SCHEDULE="30 1 * * *" BACKUP_KEEP_DAYS=90 ./backup.sh install-cron
```

Cron output is stored in `/opt/InsightFlow/backups/backup.log`. Remove the schedule with `./backup.sh remove-cron`.

## Restore on the existing server

Restoring replaces the current PostgreSQL database and uploaded media. The application is stopped during recovery. Create a safety backup first:

```bash
cd /opt/InsightFlow
./backup.sh backup
./backup.sh list
./backup.sh verify InsightFlow_full_YYYYMMDDTHHMMSSZ.tar.gz
./backup.sh restore InsightFlow_full_YYYYMMDDTHHMMSSZ.tar.gz
```

Type `RESTORE` when prompted. For an unattended emergency restore:

```bash
./backup.sh restore latest --yes
```

Then verify the deployment:

```bash
docker compose -f docker-compose.customer.yml ps
docker compose -f docker-compose.customer.yml logs backend --tail=100
```

Log in and confirm that surveys, users, results, and uploaded photos are present.

## Recover onto a replacement server

1. Install Docker Engine and the Docker Compose plugin.
2. Copy the project and a backup archive to `/opt/InsightFlow`.
3. Extract and review the archived configuration before copying it into place.
4. Start PostgreSQL and Redis, then restore.

```bash
cd /opt/InsightFlow
mkdir -p /tmp/InsightFlow-recovery/config
tar -xzf backups/InsightFlow_full_YYYYMMDDTHHMMSSZ.tar.gz -C /tmp/InsightFlow-recovery
tar -xzf /tmp/InsightFlow-recovery/config.tar.gz -C /tmp/InsightFlow-recovery/config
# Review configuration, then copy the required files into /opt/InsightFlow.
docker compose -f docker-compose.customer.yml up -d db redis
./backup.sh restore backups/InsightFlow_full_YYYYMMDDTHHMMSSZ.tar.gz
```

## Operational checklist

- Check `backup.log` daily or connect it to monitoring.
- Run `./backup.sh verify latest` at least weekly.
- Copy backups off-server; the same disk does not protect against disk loss or ransomware.
- Test recovery on a separate server at least every three months.
- Protect archives like production secrets: they include data, `.env`, and private SSL keys.
